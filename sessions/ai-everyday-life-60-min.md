# Understanding AI in everyday life — a 60-minute introduction

**Status:** formative session plan; not piloted  
**Audience:** adults and older secondary learners, adapted to the setting  
**Aim:** explain an everyday AI service, identify an uncertainty, and set a practical boundary  
**Source:** [Understanding AI in Everyday Life](https://github.com/TrivianInstitute/interaction-literacy/tree/main/orientation), especially lessons 01–03  
**Materials:** this page, paper or an accessible writing/dictation surface; no account, device demonstration, or technical background required  
**Output:** a service map and a revised use decision

This session introduces selected ideas from the four-lesson orientation. It does not replace the full pathway. Read the source lessons and their evidence notes before facilitating; use their definitions when a technical question arises.

## Prepare

Provide the fictional service description below in advance or read it aloud. Offer writing, drawing, dictation, paired explanation, or observation. Keep assistive technology and agreed language support available throughout. Learners may analyze the fictional service without describing any personal digital use.

### Fictional service: Community Guide

A library is considering **Community Guide**, an invented service with several features. It places suggested events in an order chosen using a visitor's selected interests and past clicks. It uses a language model to draft a description of each event. A separate feature can retrieve pages from the library's event calendar. If a staff member grants permission, the service can send event reminders.

The service description does not say which information reaches the language model, how long records are retained, or whether every draft uses the calendar. The interface displays: “Your personal guide to what matters.” The library has not yet decided whether to adopt it.

## Run the session

| Time | Activity | Facilitation focus |
| --- | --- | --- |
| 0–5 | Read the case and choose a response mode. Ask what the service appears to do. | Invite a first explanation without rewarding technical vocabulary. |
| 5–15 | Map four functions: ordering suggestions, generating descriptions, retrieving calendar information, and sending reminders. | One service can combine different mechanisms. The case specifies these features; branding alone would not establish them. |
| 15–25 | Explain training, the current request/context, and retrieval using orientation lesson 02. Ask which step could supply today's event date. | Training does not by itself provide a live calendar. Retrieval can supply a source, but the draft still needs checking. |
| 25–40 | Create a service map using the prompts below. Work independently or with a partner. | Ask who is affected, what is unknown, and which decision remains with the library or visitor. |
| 40–50 | Introduce the changed condition below. Revise the use decision. | A specific new fact should change a check, permission, or proposed use. |
| 50–60 | Compare the initial and revised decisions. Each learner explains one boundary and one question for the provider. | Observe reasoning; do not grade willingness to adopt AI. |

## Service-map prompts

1. What is the person's purpose? Which service function might support it?
2. Which information is supplied, retrieved, inferred, or still unknown? Keep those categories separate.
3. What could a fluent event description get wrong? Where would you check that claim?
4. Who may approve a reminder, and who may receive it? What may the service prepare before approval?
5. Who could be missed by the recommendations or unable to use the interface? What equivalent route could the library offer?
6. What would you ask about data retention, deletion, or use for training before providing personal information? Record an unanswered question as unanswered.

**Changed condition:** A calendar event has been canceled, but the draft description still invites visitors to attend. The provider explains that this particular draft was produced without calendar retrieval. The reminder feature has not sent anything yet.

Ask learners to revise both the factual check and the action boundary. Discuss who should correct the description and how visitors would learn of a cancellation if a message had already gone out.

## A plausible response and feedback

“Community Guide combines ranking, generation, retrieval, and possible outward action. We would use a draft only after checking the current library calendar. Sending reminders requires an authorized staff decision and a current recipient list. After learning that the canceled event was drafted without retrieval, we would stop that reminder and correct the description. We would ask the provider which data is retained and ensure visitors can use a staff-assisted or plain calendar route.”

Other decisions, including declining the service or running a limited trial, can be well reasoned. A strong response explains a mechanism, marks an unknown, names an affected person, and changes a concrete decision when the facts change. “The AI knows me” or “the AI is always wrong” needs a more specific account.

Use the [reasoning evidence guide](../assessment/reasoning-evidence.md). Ask one follow-up question and invite a revision. An oral explanation or diagram can show the same learning as a written map.
